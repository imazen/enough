# zenav1-svt progress diagnostics — 2026-10-01 measurement

This is a dated experiment using how-far head `d61d9a5`, before the current
v2 API and separate `how-far-really` crate. It is not a production integration
or an encoder throughput benchmark. The underlying zenav1-svt checkout is
`/home/lilith/work/zen/zenav1-svt`, branch `codex/howfar-probe`, committed head

## What ran

The real raw encoder encoded two identical 8-bit planar 4:2:0 frames at CQP 40,
preset 0, SB64. Ordinary correctness probes retained their uniform 64×64 input.
The manual timing probe used 512×512 patterned luma with tightly packed stride
512, and constant U/V planes of 256×256 with stride 256. Luma was generated by
`((i * 73) ^ ((i / 512) * 131)) & 255`. This gives a reproducible workload that
is less trivial than uniform pixels; it is not a representative photo/video
corpus. The two-frame output was 120,703 bytes.

The terminal identified the host as r5900xt. Cargo used its optimized test
profile with debug information. Jobs ran serially under the repository's
`run-heavy --mem 12G` wrapper. Timings include profiling overhead and were not
paired, CPU-pinned instruction measurements.

| Observation | Measured result |
| --- | --- |
| Outer two-frame phase | About 100–103 ms; 4 checks, 2 completed-frame reports |
| Longest outer report/check gap | About 84–87 ms before the first completed-frame checkpoint |
| Flush | About 0.0005–0.001 ms for this input/configuration |
| Separate inner first-frame stop span | About 78–85 ms; 1,558 checks |
| Inner longest check gap in the final run | 0.475328 ms |

The outer `DiagnosticPulse` measured only the borrowed pulse calls around the
encoder. A separate owned stop wrapper entered `EncodePipeline::with_stop`
and measured its internal checkpoints. Those two spans used separate profilers;
they establish different observations and cannot be correlated by timestamp.
The later Sonnet fix allows covering spans on one profiler to explain this
boundary. Current v2 also supplies an instrumented owned `stage.share()` view.

## What the results imply

Frame-completion reports leave a visible plateau while the first frame encodes.
The inner cancellation path already checks frequently on this workload. Adding
more cancellation checks at the outer frame boundary cannot make its progress
bar smoother. Meaningful progress within a frame needs a reporting seam in the
encoder: for example completed superblocks in mode decision, then separate
filtering and entropy phases. One check must not automatically become one
completed unit; the 1,558 checks cover different loops and costs.

The first diagnostic version also proposed changing the two-stage weights from
9:1 to 99:1 when the weight-difference threshold was reduced to 5 percentage
points. The pending probe applies that change only to its two-frame CQP plan.
Treat it as provisional: current diagnostics preserve the declared weight of
negligible stages instead of calibrating flush from a single near-zero sample.
Do not promote 99:1 to general codec defaults without measuring representative
inputs, rate-control modes, buffering and flush behavior.

No subscriber callback was measured by this zenav1-svt experiment. It does not
validate a 10 ms callback duration/cadence target or browser presentation latency.
Those remain separately instrumented consumer measurements.
